# 第06章　等式与重写：相等的东西何时能替换

用公式证明程序性质时，经常需要把一个表达式换成另一个。假设已经知道用户编号 a 与 b 相等，那么把 a 交给同一个查询函数 f，结果应与把 b 交给 f 相等。这里并不需要知道 f 的实现，只需要相同输入得到相同输出的函数结构。形式化工具把这种常见替换变成明确、可检查的步骤。

先区分三件事：两个表达式经过定义计算后已经相同；我们手里有它们相等的证明；人类觉得它们代表同一个意思。这三种情况的处理方式不同。前两者可以在形式系统内部得到精确解释；第三种通常还需要补充定义和定理。

![用 a 等于 b 的证据，把函数输入中的 a 替换成 b](../assets/images/fig-06.svg)

图6：重写保持表达式的外部结构 f 不变，只沿已知等式更换输入。等式可以正向或反向使用，方向由希望得到的目标形式决定。

## 先从计算能完成的等式开始

```lean
example : (fun n : Nat => n) 3 = 3 := by
  rfl
```

```rocq
Example identity_three : (fun n : nat => n) 3 = 3.
Proof.
  reflexivity.
Qed.
```

左边把恒等函数应用于 3，按函数应用的计算规则就得到 3。因此目标两边可以归约成同一个表达式。我们没有枚举很多输入，也没有调用一个外部数学求解器。

Lean 的 `rfl` 与 Rocq 的 `reflexivity` 都适合许多这类目标，但它们不是“只要数学上相等就能通过”的万能按钮。若等式需要某个代数定理，例如两个任意自然数相加的交换律，通常不能仅靠展开定义把两边直接算成同一项。关于 Lean 的等式与计算，可读官方 [Quantifiers and Equality](https://lean-lang.org/theorem_proving_in_lean4/Quantifiers-and-Equality/)；Rocq 的计算归约规则见 [Conversion rules](https://rocq-prover.org/doc/V9.0.0/refman/language/core/conversion.html)。

这里还有一个实用判断：表达式中出现未知变量时，递归函数未必能继续展开。能算出 `f 3`，不代表能把 `f n` 完全算完。n 可能有不同结构，而函数要先知道属于哪个分支。下一章的归纳，就是在计算卡住时利用数据结构继续证明的一种方法。

## 让等式证据发挥作用

```lean
theorem replaceArg (f : Nat → Nat) (a b : Nat) (h : a = b) :
    f a = f b := by
  rw [h]
```

执行重写前，我们有 `h : a = b`，目标是 `f a = f b`。`rw [h]` 沿 h 的方向，把目标中的 a 换成 b，留下自反等式 `f b = f b`；此处 Lean 的 `rw` 会完成这个自反目标。不要把这理解成“h 证明 f a = f b”：h 证明的是 a = b，重写步骤负责把证据带入更大的表达式。

```rocq
Theorem replace_arg : forall (f : nat -> nat) (a b : nat),
  a = b -> f a = f b.
Proof.
  intros f a b h.
  rewrite h.
  reflexivity.
Qed.
```

Rocq 这里把最后的自反性写成单独一步，更容易观察重写后的状态。两段证明不是逐行翻译的语法教材，而是同一推理结构的两种实现：接收参数，利用等式，完成相同项的比较。

如果已有的等式写成 `h : b = a`，希望把 a 换成 b，就需要反向使用它。Lean 写 `rw [← h]`，Rocq 写 `rewrite <- h.`。方向选错不一定意味着逻辑错误；它可能只是把目标变得更复杂，或让后续想使用的引理找不到对应形式。策略语法可分别查 [Lean Tactics](https://lean-lang.org/theorem_proving_in_lean4/Tactics/) 和 [Rocq Tactics](https://rocq-prover.org/doc/V9.0.0/refman/proof-engine/tactics.html)。

## 重写目标，也可以整理假设

假设上下文还有 `ha : R a`，其中 R 是某种性质，比如“编号对应的记录满足校验规则”。要把它转成 R b，可以沿 a = b 在 ha 中重写。Lean 的形式是 `rw [h] at ha`；Rocq 是 `rewrite h in ha.`。目标区没变，但已知区现在出现了更有用的证据。

不要为了让所有东西长得一样，盲目重写整个上下文。证明中可能同时需要原来的 a 与替换后的 b；过早替换会隐藏你想表达的关系。一个好习惯是在纸上先写：“我要把哪一个表达式改成什么，方便使用哪条事实？”如果这句话说不出来，继续尝试重写往往只会积累偶然成功的脚本。

对于依赖类型，替换还可能涉及类型本身。例如长度为 a 的向量与长度为 b 的向量，在 a = b 的条件下需要沿等式搬运。它比普通函数输入替换更复杂。本章先处理非依赖表达式；遇到向量类型时，应把“值如何变换”与“类型如何对齐”分别看清，而不能当作普通字符串替换。

## 化简为什么能很方便，也可能令人迷惑

Lean 中经常见到 `simp [某个定义, 某条引理]`。它把指定事实与已有化简规则用于目标整理。Rocq 的 `simpl` 更侧重按计算规则化简表达式；若需要利用已经证明的等式，经常还会显式写 `rewrite`。二者名称相近，但不能机械地视为同一操作。

例如，一段 Lean 证明写 `simp [join, count, ih]`，其中可能同时发生定义展开、应用归纳假设、使用已有的自然数引理。若只看到“自动通过”，会错过证明真正的结构。练习时可以把目标写出来，尝试先展开一层定义，再指出 ih 匹配的位置，最后处理剩余等式。

自动化不是降低严谨性。关键是它最后提交的证据是否按工具的可信机制检查，以及读者能否维护脚本依赖。实际工程可以优先用简洁的自动化；教学阶段则应知道自动化替你省略了哪些中间状态。复杂自动化与库的选择会在第10章继续讨论。

## 一次有目标的排错

假设你试图用 a = b 改写 f c，工具报告没有找到匹配项。先检查 c 是否就是 a；如果 c 是另一个变量，仅凭名字相似没有任何关系。再检查等式是否在当前分支的上下文里；在兄弟分支中引入的局部假设不能直接使用。最后检查重写方向，以及表达式是否被另一个定义包住，需要先展开该定义才能显露匹配项。

这几步比立刻加入更强的自动策略更有教学价值。错误经常出在规格、变量或作用域，而不是工具“证明能力不够”。

练习一：给定 h : a = b，证明 b = a。Lean 可用 `exact h.symm`；Rocq 可写 `symmetry. exact h.`。这一步表达等式对称性，并没有改变假设 h 的内容。

练习二：给定 h₁ : a = b 与 h₂ : b = c，证明 a = c。Lean 可写 `exact h₁.trans h₂`。Rocq 可写 `rewrite h1. exact h2.`，其中先把目标 a = c 变成 b = c。请特别检查 h₂ 的方向：若给出的是 c = b，还要先对称或反向使用。

练习三：为什么 `x + y = y + x` 不应被描述为“交换一下字符串”？答案是加法的交换律属于该运算的已证明性质；对任意二元运算，同样的交换未必成立。形式化工具要求我们交出性质的依据，正好阻止把某个熟悉运算的经验误推广到所有符号。
