# 第02章　命题、类型与证据

阅读 Lean 或 Rocq 时，经常会看到冒号。`n : Nat` 或 `n : nat` 表示 `n` 是自然数；`h : P` 则表示 `h` 是命题 `P` 的一个证明。在两类表达式中，冒号都在陈述“左边的项具有右边的类型”。不同之处在于，我们怎样解释右边的对象。

这就是本章的起点：命题可以表示为类型，证明可以表示为该类型的项。它使证明检查与类型检查联系起来，通常称为 Curry–Howard 对应。[资料：Lean《Propositions and Proofs》§3.1](https://lean-lang.org/theorem_proving_in_lean4/Propositions-and-Proofs/)。这里的“证明是项”不是说任意可运行程序都是数学证明；项必须具有所声明命题对应的类型，并符合系统规则。

## 2.1 命题不是布尔值的另一种拼法

布尔值有 `true`、`false` 两个取值，常用于可执行判断。命题则表达需要讨论的逻辑陈述。例如“对所有自然数，某性质成立”不是运行一次就自动得到的布尔结果。

一个程序可以返回 `true`，却没有附带“它为什么判断正确”的证明。要把布尔判断连接到命题，通常需要额外定理，例如“检查器返回 `true` 当且仅当列表有序”。这个连接本身就是可验证软件的重要组成部分。

Lean 与 Rocq 都使用 `Prop` 表示命题所在的层次；它与数据使用的类型层次有区别。初学阶段先记住用法：定义数字和列表时关注数据，陈述性质时关注命题，构造证明时关注能否提供匹配证据。不要把 `Prop` 当成所有数据类型的总称。

## 2.2 蕴含为什么像函数

假设已经有 `hp : P` 和 `f : P → Q`，那么 `f hp` 具有类型 `Q`。把它读作逻辑，就是：已知 `P`，且已知 `P` 蕴含 `Q`，因此得到 `Q`。

更值得体会的是如何证明 `P → P`。我们不需要无条件证明 `P`。只需要说明：如果给我一个 `P` 的证据，我可以原样交还。对应的证明项是恒等函数。

Lean 写法：

```lean
example (P : Prop) : P → P :=
  fun h => h
```

Rocq 写法：

```coq
Definition identity_proof (P : Prop) : P -> P :=
  fun h => h.
```

`fun` 引入函数，`h` 是它接收的证据。Rocq 中，`A -> B` 也是非依赖函数类型的记法；当 `A`、`B` 为命题时，它对应逻辑蕴含。[资料：Rocq 9.0《Functions and assumptions》](https://rocq-prover.org/doc/V9.0.0/refman/language/core/assumptions.html)。后续章节会用策略写同一证明，使读者能同时理解证明项与交互步骤。

## 2.3 合取、析取与存在的证据

`P ∧ Q` 表示两件事都成立。证明时应分别提供 `P` 的证据和 `Q` 的证据；使用时可以取出其中一份。假设你有“订单已付款且库存充足”，便能得到“订单已付款”。这里做的是拆解现有证据，并没有额外证明库存规则。

`P ∨ Q` 表示至少一边成立。要建立它，可以选择一边并提供那边的证据；要使用它，通常必须分别处理两种可能。仅凭“付款或获准赊账”，不能直接宣布已经付款。

存在命题 `∃ x, R x` 要求一个见证 `x`，以及 `R x` 的证据。比如“存在一个自然数等于自己”，可以选择零，再证明零等于零。写存在证明时，选出见证只是第一步；选择一个对象不自动保证它满足性质。

这些对应关系提供一种可靠的初步思路：先读目标最外层的逻辑结构，再决定证据的形状，而不是盲目尝试策略名称。

## 2.4 全称量词与依赖类型

命题“每个自然数都满足 `R`”要求一个统一方法：给定任意自然数 `n`，能够构造 `R n` 的证明。它不是只处理零、一个特殊样本或当前计算机里出现过的数。

类型也可以依赖数值。设一个向量类型记录长度，那么“长度为三的向量”与“长度为四的向量”便可由类型区分。访问函数若要求索引小于长度，调用时就必须提供相应依据。某些原本在运行时才能发现的误用，由此可以在形式检查阶段暴露。

不过，把条件写进类型不意味着所有条件都会自动证明。条件越精细，调用者越可能承担额外的证明义务。合适的设计应让结构帮助表达关键约束，同时避免把无关细节塞进每个接口。

## 2.5 构造性与经典逻辑

有些证明明确给出对象或构造方法；另一些依赖经典推理原则。例如排中律说，任意命题 `P`，`P` 或其否定成立。它不等于提供一个能对任意命题运行并判定真假的算法。

Lean 可以使用经典逻辑支持，Rocq 也可以显式引入经典逻辑库或公理。两者都不应被简单归类成“只能构造”或“只能经典”。具体定理依赖什么，应查看实际使用的声明与公理。[资料：Lean《Axioms and Computation》](https://lean-lang.org/theorem_proving_in_lean4/Axioms-and-Computation/)；[Rocq 标准库《Classical_Prop》](https://rocq-prover.org/doc/V9.0.0/stdlib/Stdlib.Logic.Classical_Prop.html)。

第一次学习时，可以先用能直接解释的构造式证明：给出函数、拆开合取、选择见证、按数据结构分情况。遇到经典推理，再明确说明它解决了哪一步、引入了什么依赖。无需把哲学立场变成入门门槛，但应学会辨认推理条件。

## 2.6 把类型错误当成线索

若目标是 `P ∧ Q`，手里只有 `hp : P`，系统拒绝 `exact hp`，并非否定 `P`。它是在指出证据形状不够：当前需要一对证据，给出的却只有左边一份。

若目标是 `Q`，手里有 `f : P → Q`，直接交出 `f` 也不行，因为 `f` 仍在等待 `P` 的证据。这类错误类似函数漏传参数，但逻辑含义更明确：论证缺少前提。

**练习。** `P → Q` 与 `Q → P` 能否互换？若已知两者，得到什么？

**参考解答。** 一般不能互换。前者提供从 `P` 到 `Q` 的证据转换，后者方向相反。两者同时成立时可构造逻辑等价 `P ↔ Q`。一个方向的充分条件不自动成为必要条件。
