# 第11章　真实项目：从小定理走向可复查成果

列表追加的性质只有几行，实际数学与软件项目却可能涉及多年工作。规模增长时，真正增加的往往不是单个推理步骤有多神奇，而是需要共同建立的定义、接口、库和信任说明。本章选择三个来源可追溯的项目，分别观察编译器、有限组合数学与现代抽象数学怎样进入证明助手。

## 11.1 CompCert：保持程序的意思

编译器把一种语言翻译成另一种语言，过程中会优化、删除和重组操作。一个优化即使通过了大量测试，也可能在某个边界条件下改变程序行为。编译正确性要回答的问题是：目标程序的行为与源语言语义规定的行为保持什么关系。

CompCert 是以 Rocq/Coq 证明为基础的验证编译器。官方手册明确说明其语义保持定理连接的两端：一端是经过预处理、解析、类型检查与 elaboration 后的 CompCert C 抽象语法树，另一端是汇编与链接之前的 Asm 抽象语法树。这个边界值得反复阅读，因为它说明“编译器已验证”具体指哪一段转换。[来源：CompCert 手册，第 1 章](https://compcert.org/man/manual001.html)

可以用一个简化例子理解：源程序读取 `x`，计算 `x + 0`，然后输出结果。若优化把计算替换为直接使用 `x`，证明需要说明在相应类型与语言语义下，外部可观察行为保持。真实编译器中的证明比这个例子复杂得多，因为还涉及内存、调用、控制流和目标体系结构。

这里有两个常见误读。第一，编译器正确不意味着输入程序没有漏洞；源程序若正确表达了一个错误算法，保留语义只会把错误算法准确翻译过去。第二，不能跳过语言语义的适用条件。包含未定义行为的 C 程序，无法仅凭“用了验证编译器”取得任意期望保证。

CompCert 的可信计算基研究进一步分析了证明系统、未验证组件和外围工具等依赖。它提供了一种很有用的阅读方法：不要只问“有没有形式化证明”，还要画出证明覆盖的部件、假设与实际工具之间的连接。[来源：Monniaux、Boulmé，The Trusted Computing Base of the CompCert Verified Compiler](https://arxiv.org/abs/2201.10280)

对本书读者而言，最可迁移的启发是“保留什么”。当你验证一个格式转换器、解释器或代码优化时，先定义两端的意义，再陈述它们之间的关系，会比笼统地声称转换“无损”更清楚。

## 11.2 四色定理：计算也能成为证明的一部分

四色定理涉及平面地图的着色：在适当形式化的邻接条件下，四种颜色足以区分相邻区域。直接枚举所有地图显然不可行；理论工作要把无限问题化成可处理的结构和有限检查。

Rocq 社区维护的 fourcolor 项目包含四色定理的形式化证明，以及陈述和证明该结果所需的理论。项目源代码可以被查看、构建和继续维护，因此读者面对的不只是“计算机说它正确”的一句公告。[来源：fourcolor 项目](https://github.com/rocq-community/fourcolor)

这个案例提示我们区分两类活动。一类是对大量例子运行程序，观察都能着色；另一类是证明某个有限检验过程所检查的条件足以推出一般结论，再让检查过程确认这些条件。后者能把计算结果接入数学推理，但中间那座桥梁本身必须建立起来。

在 Rocq 中，这类思想与“小规模反射”密切相关：把某些逻辑问题映射到可计算的布尔判断，并证明判断与命题之间的联系。Mathematical Components 的历史与四色定理工作相连，SSReflect 也成为这一生态的重要证明语言。[来源：Mathematical Components 项目介绍](https://math-comp.github.io/)

用一个微型例子说明这种连接：程序判断一个自然数是否为偶数，返回 `true`；逻辑命题则说“存在自然数 `k`，使 `n = 2*k`”。如果只运行判断，拿到的是一个布尔值；如果证明两种说法等价，计算就能为逻辑结论提供受控的入口。这个例子仅解释方法，不等同于四色定理的实际算法。

## 11.3 Liquid Tensor Experiment：抽象数学需要基础设施

Lean 社区在 2022 年宣布完成 Liquid Tensor Experiment，形式化验证了相关液态向量空间的主要定理。项目依靠多人协作、数学支持以及 mathlib 中的既有理论。原项目使用当时的 Lean 体系，阅读历史代码时应注意它不一定与今天的新建 Lean 4 工程直接兼容。[来源：Lean 社区完成公告](https://leanprover-community.github.io/blog/posts/lte-final/)

非专业读者不必先学习其中全部数学。更值得观察的是工程结构：自然语言中的一个定理，依赖大量背景对象；这些对象进入系统后，需要定义与引理接口；不同参与者才能在稳定接口上分别工作。这与软件模块有相似之处，但验证对象是数学陈述和证据。

如果一个项目只有最终定理，没有可读的定义和依赖说明，即便检查成功，外部读者仍然难以判断它是否表达了原问题。形式化工程因此同时需要机器可检查的源文件与人类可追踪的解释。两者服务的目的不同：前者核查推理，后者帮助审阅建模。

## 11.4 怎样读一个真实形式化项目

初次进入仓库，可以按四个问题阅读。

1. 它声称形式化的核心定理是什么？先找到实际声明，而非只看 README 的概述。
2. 关键对象如何定义？词语熟悉，不代表形式化定义必然与你理解的一样。
3. 构建需要什么版本和依赖？能否在明确环境中重现？
4. 定理依赖哪些公理、工具与边界外假设？这些依赖是否与目标用途相容？

练习：一个项目已经证明“优化后程序与输入程序返回相同整数”，能否推出它们执行时间相同？不能。返回值关系没有陈述时间。若还要验证性能上界，就应在模型中定义代价并证明相应关系。

本章三个项目说明的共同事实是：形式化把承诺变成可查的对象，但承诺的内容仍须仔细阅读。真正值得学习的能力，是沿着定理、定义和依赖逐层追问，直到知道结论可以用在哪里。
