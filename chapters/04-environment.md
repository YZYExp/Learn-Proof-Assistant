# 第04章　建立可以重新检查的工作环境

证明书中的代码应当能够被重新检查，而不仅是在某张截图里显示过成功。为此，需要把源文件、工具版本、依赖与运行方式放在一起考虑。安装本身不是本书的学习目标，但一个清楚的环境能避免把工具问题误判为数学问题。

本书使用 Lean 4 语法与 Rocq 的现代命令说明。Rocq 延续了 Coq 的大量语言与生态，旧资料中的名称仍会出现；代码围栏使用 `coq` 只是通用语法高亮标签，不表示正文退回旧版本。学习时应选择一个已发布的工具链，固定后再运行整组示例，而不是每章跟随网站的 `latest` 或 `master` 更新。

## 4.1 Lean：编辑器、工具链与工程

Lean 官方入门安装路径以 VS Code 和官方 Lean 4 扩展为起点，由扩展引导配置工具链。若使用其他编辑器或命令行，可以按官方手动安装说明进行。安装方法会随平台演进，本书不复制可能过期的下载地址。[资料：Lean 官方安装页](https://lean-lang.org/install/)。

先创建一个单独的学习目录，把示例保存为 `First.lean`：

```lean
example (P : Prop) : P → P := by
  intro h
  exact h
```

在该目录执行：

```bash
lean --version
lean First.lean
```

第一条记录实际使用的版本，第二条检查文件。正常的批处理检查未必输出“证明成功”这四个字；应同时检查退出状态与诊断，不能把终端安静直接等同于运行了预期文件。

学习进入多文件阶段后，使用 Lake 管理工程与依赖。Lake 是 Lean 的构建工具，`lake build` 构建工程，`lake env lean First.lean` 在工程环境内检查指定文件。工程中的 `lean-toolchain` 用来指定工具链；还应保留 Lake 配置和依赖清单。[资料：Lean 官方《Lake》](https://lean-lang.org/doc/reference/latest/Build-Tools-and-Distribution/Lake/)及其相邻的 Elan 文档。

不要随意把其他项目的依赖版本复制进新项目。如果某个 mathlib 项目已经指定 Lean 版本，应先采用它的工具链约定，再考虑升级。库源码、编译产物与编译器不匹配时，错误未必来自证明本身。

## 4.2 Rocq：系统与编辑器需要配套

Rocq 官方提供按 Linux、macOS、Windows 区分的安装说明。Rocq Platform 的价值在于提供协调过的一组证明器、库与相关工具；希望细致控制依赖时，也可以沿官方说明使用 opam 等方案。[资料：Rocq 官方安装页](https://rocq-prover.org/install)。

编辑器并不等于证明器。使用 VS Code 的 VsRocq 时，还需要兼容的语言服务器；扩展与服务器的版本应匹配。若终端能够检查文件，但编辑器始终无法显示状态，应先检查编辑器选用的环境和服务器，而不是修改已经通过的证明。

把下面内容保存为 `First.v`：

```coq
Theorem identity_proof : forall P : Prop, P -> P.
Proof.
  intros P h.
  exact h.
Qed.
```

现代 Rocq 命令行可以使用：

```bash
rocq --version
rocq compile First.v
```

`rocq compile` 检查 `.v` 文件并生成编译库文件。旧 Coq 教程常见 `coqc First.v`；一些发行版保留兼容命令，但不能假定每个安装环境都有相同别名。先查看本机帮助与对应版本手册，再采用一套一致命令。[资料：Rocq《The Rocq Prover commands》](https://rocq-prover.org/doc/V9.0.0/refman/practical-tools/coq-commands.html)。

## 4.3 证明代码实际经历了什么

编辑器读取文件后，会把内容发送给相关语言服务。证明器解析语法、解析名字、补足可推断信息并处理策略，最终形成需要检查的形式对象。Lean 文档把这类从用户语法到核心表达的处理称为细化；核心检查器检查生成项是否符合类型规则。[资料：Lean《Elaboration and Compilation》](https://lean-lang.org/doc/reference/latest/Elaboration-and-Compilation/)。

这解释了两个常见现象。第一，界面能高亮不代表证明已经检查：高亮可能只依赖文本规则。第二，某处后面的状态没有更新，可能是前面有语法或环境错误，导致处理没有推进。排错应从最早的相关错误开始，后续一连串错误可能只是它的结果。

批处理与交互检查各有用途。交互模式方便观察一步一步的目标；批处理适合确认整个文件或工程在指定环境下能完整通过。一本书的代码若只在交互会话里试过，没有从干净会话检查整份文件，仍可能依赖未记录的临时定义。

## 4.4 三类文件，三种管理方式

| 内容 | 例子 | 建议 |
|---|---|---|
| 需要长期保存的输入 | `.lean`、`.v`、依赖配置、版本记录 | 纳入版本管理 |
| 可以重建的输出 | Lean、Rocq 的编译产物与缓存 | 按项目规范忽略或单独管理 |
| 便于诊断的记录 | 检查命令、版本、错误日志 | 记录必要信息，避免混入凭据 |

版本固定的意义不是永不升级，而是让一次结果有可复现的条件。升级时可以建立分支，整体更新依赖，运行检查，再修订受影响的证明。若只在自己的电脑上逐个修到能用，却不更新版本记录，协作者仍无法复现。

## 4.5 遇到问题时，制作最小例子

报错时先复制出最小文件：保留必要导入、定义、定理与失败步骤。记录实际版本、完整命令和第一条相关错误。若删去某个导入后问题消失，说明它可能影响名字或记号；若只有工程里失败，则检查路径和依赖设置。

**练习。** 同一份文件，编辑器没有红线，但终端检查失败，可以宣布证明已完成吗？

**参考解答。** 不能。先确认文件已经保存，终端与编辑器使用同一工具链和依赖，并检查编辑器处理是否已经推进到文件末尾。结果应附带明确的检查方式。对尚未实际执行的示例，应标记为静态审阅，不能把预期可运行写成已验证。

完成本章的标志不是装齐最多工具，而是能保存一个文件、观察证明状态、运行完整检查，并说明结果对应哪套环境。接下来便可以把注意力放回证明本身。
